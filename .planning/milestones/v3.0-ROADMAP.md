### Phase 5: HCVGLUE Per-Sample Parallel Refactor

**Status**: PAUSED (2/3 plans complete; Plan 03 Task 2 blocked by `run-glue.sh` container defects — resume via `/gsd-resume-work`, see `.continue-here.md`). v2.0 milestone, NOT part of v3.0.
**Goal**: HCVGLUE runs as one self-contained container task per sample — parallel-safe and hermetic, with no shared MySQL container and no bespoke docker-spawning logic — while `*.json`/`*.html` outputs and everything downstream stay unchanged.
**Depends on**: Phase 4 (v1.0 complete; HCVGLUE/GLUE_PARSER wiring is the current baseline)
**Requirements**: GLUE-01, GLUE-02, GLUE-03, GLUE-04, GLUE-05, GLUE-06
**Success Criteria** (what must be TRUE):

  1. **Research gate resolved (GLUE-01)**: A documented spike determines whether HCVGLUE can run without per-task MySQL download/install (e.g. a pre-baked image with the HCV GLUE project already loaded and `installGlueProject.sh` pre-run). If viable → criteria 2-6 proceed. If not viable → the phase closes with the current collected-channel architecture preserved, the limitation documented, and GLUE-02/GLUE-03 explicitly marked blocked.
  2. **Per-sample task fan-out (GLUE-02)**: The HCVGLUE process consumes a per-sample channel (one task per sample, `collect()` dropped from both the `MAJOR_MAPPING`/`MINOR_MAPPING` aligned feed and the `HCV_GLUE_PARSER` input wiring), so N samples produce N independent HCVGLUE tasks.
  3. **Concurrent isolation (GLUE-03)**: Multiple HCVGLUE tasks run simultaneously with no container-name collisions and no shared MySQL state — a multi-sample run completes without cross-task interference.
  4. **Output compatibility (GLUE-04)**: Each sample still emits `*.json` + `*.html` in the existing format; `HCV_GLUE_PARSER` consumes them unchanged and the resulting `Summary.csv` is identical in structure to the pre-refactor output.
  5. **Multi-profile portability (GLUE-05)**: The refactored process runs correctly under the Docker, Singularity/Apptainer, and Podman container profiles.
  6. **Script cleanup (GLUE-06)**: `bin/run_hcvglue.sh` is simplified or replaced — no `apt-get` inside containers, no deprecated `--link` flag, no hardcoded container names.

### Phase 6: Neutral Candidate Selection

**Goal**: Reference selection during the run becomes dominance-neutral — it ranks N candidate references by read recruitment and maps each one independently — so no major/minor semantics are baked in before the evidence is in. This is the structural foundation the later classification depends on.
**Depends on**: Phase 4 (v1.0 selection/mapping is the baseline; runs in parallel with the paused Phase 5, which it does not depend on)
**Requirements**: REFSEL-01, REFSEL-02, REFSEL-03
**Success Criteria** (what must be TRUE):

  1. After first-pass mapping, candidate references are emitted as a neutrally-ranked ordered set (`cand_1..cand_n`) ordered by read recruitment, with no "major"/"minor" label assigned during the run (`modules/local/parsefirstmapping/` + `bin/summarize_mapping_to_all_references.R`).
  2. The number of candidates is controlled by a single parameter (default 2); running with the default produces the same two candidate slots the pipeline selects today.
  3. Each selected candidate is independently targeted-mapped through one uniform path (no asymmetric `MAJOR_MAPPING`/`MINOR_MAPPING` aliases in `workflows/hcvtyper.nf`); every candidate gets the same mapping stats.
  4. Per-candidate `confirmation_status` replaces the old `gate_flag`/`minor_call` plumbing, carried through channels and into the summary inputs without index misalignment.
  5. With candidate count = 2 and default flags, the candidate set and per-candidate mapping outputs reproduce the current pipeline's two-slot selection on the regression fixtures.
     - **RE-SCOPED (per CONTEXT D-05 CONSEQUENCE):** Because D-05 removes `is_valid_minor()` validity filtering from selection (and D-03 ranks the 2nd candidate by reads, not coverage breadth), the 2nd candidate may legitimately differ from today's minor. Criterion #5 (golden two-slot reproduction) therefore **cannot hold standalone at Phase 6 and is NOT a Phase-6 verification blocker** — it is formally gated at Phase 9 / COMPAT-01. Phase 6 instead asserts: (a) routing topology unchanged at N=2 (two mapping slots), (b) no crash on single-candidate / no_mapping / empty-stats inputs, (c) D-06 shim integrity (`_major.fa`/`_minor.fa` written, all 10 legacy columns present, `.major.`/`.minor.` filename slot correct, `summarize.R` consumes the CSV unchanged).

### Phase 7: Per-Genotype Assembly Support

**Goal**: De novo/BLAST evidence stops being an output-only or minor-only QC artefact and becomes an independent, per-genotype "assembly support" signal computed without reference to which candidate is dominant — ready to corroborate any candidate at genotype level.
**Depends on**: Phase 6 (candidates exist as a neutral set to join evidence against)
**Requirements**: ASUP-01, ASUP-02
**Success Criteria** (what must be TRUE):

  1. For every genotype seen in the de novo contigs, assembly support is summarized as best contig length, BLAST identity, BLAST alignment length, and k-mer coverage — computed independently of the mapping/candidate result (`modules/local/blastparse/` + `bin/blast_parse.R`).
  2. Assembly support is joined to candidates at genotype level using a parameterized match level (default genotype, not subtype), so a 3b candidate is corroborated by 3a assembly support per the established genotype-match rule.
  3. A candidate with no corresponding genotype-level assembly evidence resolves to an explicit "no support" state rather than silently dropping the row (NA-fill, no row loss — consistent with the v1.0 `left_join` plumbing).
  4. With default flags and candidate count 2, the assembly-support join reproduces the de novo evidence currently attached to the minor slot for the regression fixtures.

### Phase 8: Dominance Scoring + Strain-Role Classification

**Goal**: At the summary step — and only there — each candidate is assigned a strain role (dominant / co-infection / background) driven by a combined, breadth-evenness-weighted dominance score, with background/artefact candidates surfaced explicitly rather than dropped, and an overall sample call derived from the roles. This is where the index-hopping/contamination false co-infections actually get caught.
**Depends on**: Phase 6 (neutral candidates + per-candidate mapping) AND Phase 7 (per-genotype assembly support join)
**Requirements**: SCORE-01, SCORE-02, CLASS-01, CLASS-02, CLASS-03, CLASS-04
**Success Criteria** (what must be TRUE):

  1. Each candidate gets a combined dominance score over mapped read count, k-mer coverage, and mapping coverage breadth (`bin/summarize.R`), where breadth evenness/uniformity across the genome is weighted strongly relative to raw read count.
  2. Each candidate is classified into exactly one strain role — dominant / co-infection / background — visible per-candidate in the summary output.
  3. A non-dominant candidate is reported as co-infection only when it clears the abundance floor AND has genotype-level assembly support; otherwise it is classified background/artefact ("guilty until corroborated") — verified against the benchmarked false-4g-minor case (refuted to background) and a genuine co-infection case (preserved).
  4. Background/artefact candidates appear in the output with an explicit reason (no assembly support / below floor) and are never silently dropped.
  5. An overall sample call (monoinfection / co-infection / indeterminate) is derived from the candidate roles and reported once per sample.

### Phase 9: Compatibility, Filename Migration + Regression Suite

**Goal**: The redraw ships non-breaking. The output-filename slot migration and its consumer-side parsing change land together, legacy columns are aliased for one release, the preserved HCV exceptions still hold, and the regression suite proves all of it in CI. This is the highest-risk integration phase and runs last.
**Depends on**: Phase 8 (the role-based outputs and overall sample call exist to alias against and to test)
**Requirements**: COMPAT-01, COMPAT-02, COMPAT-03, COMPAT-04, TEST-01
**Success Criteria** (what must be TRUE):

  1. Output-filename slot fields migrate `.major.`/`.minor.` → `.cand1.`/`.cand2.` in lockstep with `bin/summarize.R` parsing — the filename writer and the summary parser change in the same phase, and a full run produces correctly-parsed candidate rows with the new slot names.
  2. Legacy `Major_*`/`Minor_*` summary columns are emitted as aliases alongside the new role-based columns for one release, so a downstream consumer reading the old column names still works.
  3. With default flags and candidate count 2, the pipeline reproduces v1.0/v2.0 reporting on the golden baseline (non-breaking, COMPAT-01).
  4. The existing 1a/1b co-infection exception and 2k/1b recombinant suppression behave identically after the redraw (COMPAT-04).
  5. The CI regression suite is extended to cover candidate ranking, all three role classifications, combined-score dominance, and legacy-column/golden-baseline reproduction, and runs green in CI (TEST-01).
